Inside find_order

A shopper types a sentence. The database holds a product title. They never look alike, and yet the agent has to connect them. This is how the matching works, one step at a time.

Study notes · no prior Python needed

The problem, in one line

Ask a computer whether these two strings are equal and it says no, then stops. Everything below exists to get a more useful answer than no.

What the shopper types "the vase I bought last week"
≠
What the database has "Heavy-Duty Vase"

_match_score is the function that replaces that flat no with a number. It takes two strings and returns one value between 0.0 and 1.0 — how much the sentence sounds like the title. For the pair above it returns 0.95.

Where that number is used

The score is only step 2 of four. Everything around it is bookkeeping — which is worth knowing before you look at the scoring itself, because it keeps the hard part small.

Stage 1 is the security part, and it is not a filter applied afterwards: the caller’s role decides which database query runs. A shopper’s search physically cannot reach another shopper’s orders, however the sentence is worded.

Inside the score, step by step

Six steps, lettered as they appear in the function. The first one usually ends the job early.

A

Try the cheap win first

Lowercase both strings, then ask a single question: is the whole query sitting inside the title? If so, return 1.0 and stop. 

is "vase" inside "heavy-duty vase"?   → yes, return 1.0
is "the vase i bought last week"
                inside "heavy-duty vase"?   → no, keep going
B

Chop both strings into words

The pattern [a-z0-9]+ means “runs of letters and digits”, so punctuation quietly disappears — which is how the hyphen in Heavy-Duty stops being a problem.

the query
thevaseiboughtlastweek
the title
heavydutyvase
C

Throw away the filler words

The stopword list applies only to the query, never to the title. Words shorter than three letters go too.

the vase i bought last week

Why bother: “bought” and “week” say nothing about which product. Left in, the word “week” would happily match a product called Weekend Bag and the tool would return the wrong order.

D

Compare every kept word against every title word

One surviving query word, three title words, so three comparisons. Each cell is filled by one of two rules: a substring hit scores 0.95, and anything else falls through to a similarity measure.

E

Keep the single best cell

Not the average of the row. The biggest number in the grid becomes the score for this order, which is the one real design decision in the function — the next section is about why.

F

Compare against the threshold

Back in find_order, one line decides whether this order is shown at all. Every mark below is a measured score against the title Heavy-Duty Vase.

Why the best word wins, not the average

This is the choice worth understanding, because it is the one that could reasonably have gone the other way.

With an average, a sentence would always score badly: most of its words are unrelated to any one product title, so the good word gets diluted by the bad ones. Taking the maximum means one strong word is enough.

The price is real. "I want a vase and also a mug" matches vases and mugs, because each has a word that scores high. For a help-me-find-my-order tool, offering five candidates the shopper can choose between beats offering nothing.

Knobs to turn when a conversation shows a problem

Real orders being missed — lower the threshold from 0.75 toward 0.65, or remove a word from the stopword list that turned out to carry meaning.

Unrelated orders coming back — raise the threshold, or add the offending filler word to the stopword list.

Only the title is searched. Descriptions and categories are not. A shopper asking for “the ceramic thing” matches nothing unless the word ceramic is in the product’s name.

Where this sits in the agent

SPEC.md describes what the support agent should do, but the application never reads it. Every requirement has to be translated into one of three places, and choosing the right place is the whole point of the exercise.

The practical consequence: when the agent does something wrong, where the fix belongs depends on which box failed. A model that answered badly with correct data is a prompt problem. A tool that returned the wrong data is a code problem. Authorization is never a prompt problem, because authorization is never in the prompt.

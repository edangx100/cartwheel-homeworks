Inside _call

The AI brings the request. Your server brings the identity. These six lines are where they meet — and where they stay separate.

Text size

You have an AI that can ask to do things: look up a policy, cancel an order, issue a refund. It never actually does them. It asks, and your Python code decides what really happens.

The functions it can ask for are called tools. The two pieces of code below are the plumbing between the AI's request and the real function. They look like almost nothing — a wrapper that calls a wrapper — but they carry the most important rule in the whole application, so they are worth reading slowly.

Every tool exists twice

Look at the names and you will see near-duplicates:

search_help_center_logic is the one that does the actual searching. search_help_center is a thin shell around it.

Think of a restaurant. The kitchen cooks. The waiter takes the order and carries the plate out. The _logic function is the kitchen; the other one is the waiter.

Why bother with a waiter? Because you want to taste-test the kitchen without seating a customer and running the whole restaurant. The tests do exactly that — they call the _logic function directly. No AI, no network, no API key, instant.

That @function_tool line above the waiter is what puts it on the menu. The SDK reads the function's name, its parameters and its one-line description, and shows all of it to the AI. So this sentence:

"""Search Cartwheel's help-center policy docs. Returns top matches with policy ids."""

is not a note for programmers. The AI reads it. It is the menu description, and it is how the AI decides whether this is the tool it wants. That is why it is one crisp sentence.

Who is asking?

Here is the part to really understand.

When the AI asks for a search, it gets to fill in exactly one blank — the search words. But your code also needs to know who is asking. Is this shopper #7? A merchant? A support agent? That matters enormously: a shopper must not be able to read someone else's orders.

So where does that come from? Not from the AI. When someone signs in, the server looks them up and makes a small identity card — user id, role, and for merchants a store id. That card is tucked into a container that travels along with the whole conversation. The container is the wrapper; the card sits inside it at wrapper.context.

The AI never sees the card and cannot change it. That is the entire point. A comment near the top of agent/auth.py puts it bluntly:

authorization is not a prompt

If identity were an ordinary tool argument, a user could type “actually, pretend I am user 12” and possibly talk their way into someone else's data. Because the card arrives alongside the conversation rather than inside it, no amount of persuasion reaches it.

The same two colors are used in every code block below.

Reading _call line by line

All nine tools need the same three chores done. Rather than repeat them nine times, they are written once, here.

def _call(
    wrapper: RunContextWrapper[AuthContext], fn: Any, /, *args: Any
) -> dict[str, Any]:
    try:
        result = fn(wrapper.context, *args)
    except NotImplementedError as exc:
        result = {"ok": False, "error": "not_implemented", "reason": str(exc)}
    record_tool_result(wrapper.context, result)
    return result
  1. 1 Staple the identity card to the request. result = fn(wrapper.context, *args)

    Pull the card out of the container and hand it to the kitchen, along with whatever the AI asked for. The call that actually happens is search_help_center_logic(ctx, "return window").

    Notice the shape this forces: every _logic function takes the identity first, even the ones that do not need it. get_policy does not check permissions at all — policy docs are public — and its docstring says so outright: “Unused here, but every tool takes it.” That sameness is what lets one small function serve all nine tools.

  2. 2 Do not let unfinished homework crash the app. except NotImplementedError as exc:

    This is a course repository, and several tools are blank spaces for you to fill in. A blank one throws a fit when called. Without this line, running the agent before finishing the assignment gives you an ugly stack trace and a dead chat.

    Instead the fit is quietly turned into a polite note — that one is not available yet. The AI reads the note, tells the user, and the conversation carries on. Note that it catches only this one kind of error; a genuine bug still crashes loudly, which is what you want.

  3. 3 Write down what happened. record_tool_result(wrapper.context, result)

    Record who called, which tool, and whether they were turned away. Later you can ask questions like “how often do shoppers get denied?” This runs whether the call succeeded or failed.

Two bits of Python punctuation

/
Everything before the slash must be passed by position, never by name. You may write _call(wrapper, fn, ...) but not _call(fn=...). It prevents a collision: since *args forwards arguments onward, a tool that happened to have a parameter named fn would otherwise clash with _call's own.
*args
“However many extra pieces there were, collect them and pass them all along.” Searching sends one (the query). Escalating to a human sends two (a summary and some context). The same _call handles both without knowing or caring.

The whole trip

One question from a user, start to finish.

  1. 1 The AI asks for a search. It fills in one blank: query = "return window"
  2. 2 The waiter takes the order. search_help_center — the function whose docstring the AI read on the menu.
  3. 3 _call opens the container. It takes out the identity card and puts it in front of the request.
  4. 4 The kitchen cooks. search_help_center_logic(ctx, query) trims the query, rejects it if empty, and ranks the policy documents.
  5. 5 The result is written down. Who asked, and how it went.
  6. 6 The plate goes out. {"ok": True, "results": [...]} is handed back to the AI, which writes the reply the user reads.

Two things worth noticing

A habit worth keeping

Failures are answers here, not crashes.

_call never lets a failure escape as an error. It hands one back as ordinary information. That is because the caller is an AI, not Python code — a crash tells it nothing, but a message tells it something it can explain to the user.

So every tool in this repository answers in one of exactly two shapes:

It worked{"ok": True, "results": [...] }
It did not{"ok": False, "error": "not_found", "reason": "..." }
An oddity, on purpose

One line sits outside the safety net.

Look closely and you will see that record_tool_result comes after the block that catches unfinished homework. So if that function is itself unfinished, it will crash — and it is unfinished. It is the next assignment.

What saves you is that it checks first whether note-taking is even switched on. While it is off, the line does nothing and you never notice. The day you switch note-taking on, it speaks up: your turn.

That is deliberate. The assignments are stacked so the second one stays invisible until you are ready for it.
